# API and Database

## API

Base path `/api/v1`. Every route handler is wrapped in `withApiHandler()`; formats and error codes are in [architecture.md](architecture.md).

**Conventions:** plural kebab-case resources; `{id}` maps to an `[id]` folder; `PATCH` for partial updates; `DELETE` returns 204; status changes always use `POST /{resource}/{id}/status` with `{ "status", "reason" }`; lists accept `page`, `pageSize` (default 20, max 100), `sort` (for example `-createdAt`), `q` and named filters. `POST`, `PUT`, `PATCH`, `DELETE` need an `Origin` header equal to the site's own origin, otherwise `403`. Public endpoints are protected by a honeypot field and per-IP rate limits. Public pages read through services, so there are no public GET endpoints for content.

Endpoints are added, with request and response examples, in the phase that builds their screen. Today:

**Upload flow.** (1) The browser asks `/uploads`; the server checks purpose, extension and size and signs the upload with a random public ID in `<CLOUDINARY_FOLDER>/<applications or cv>/`, type `authenticated`, tag `pending`. (2) The browser uploads straight to Cloudinary with progress. (3) The form submits the public IDs; the server looks each file up again (folder, private, still pending, format, size), saves `fileAssets` and the record in one transaction, and only then removes the `pending` tag. (4) A file is deleted only when it is ours, still pending and fails the format or size check; a file that is saved or not ours is refused untouched. (5) The cleanup job never deletes a file the database has saved. Reference numbers come from the `counters` collection (`ADM-2026`, `SCH-2026`, `JOB-2026`, `DIR-2026`) inside the same transaction.

**File access.** A file opens for whoever holds the read permission for the record it belongs to (`applications:read` for applications, `job-applications:read` for CVs, `institutions:read` for signed agreements, `publications:read` for publication PDFs, including drafts), inside their own office unless they are Super Admin or the CEO Office. The 5-minute link and the audit entry are unchanged.

`GET /api/v1/health` returns `200 { "data": { "status": "ok" } }`, or `500 INTERNAL_ERROR` when MongoDB cannot be reached. Better Auth also serves sign-in, sign-out, password reset and change and session management under `/api/auth/*`; it is not part of `/api/v1`.

**Indexes** are declared in each schema. Unique: `referenceNumber` (applications, job applications, directives), `slug` (departments, programs, institutions, vacancies, publications, news posts), `publicId` (file assets), `applicationId` (awards), `key` (settings, rate limits). Applications: `status + type + createdAt`, `createdAt`, `programId`, `applicant.city`, `applicant.email`, `applicant.cnic`, text on applicant name and reference number. Publications: text on title and summary. Directives: `assignments.departmentId + assignments.status`, `dueDate`. Vacancies: `status + deadline`, `departmentId + status`, `createdAt`. Job applications: `vacancyId + status`, `createdAt`, `candidate.cnic`. Contact messages: `departmentId + status + createdAt`. Audit logs: `entityType + entityId + createdAt`, `actorId + createdAt`. Awards: `renewalDate + status`, `status + startDate`; an award also keeps the application's reference number and student name, so its list needs no lookup. Rate limits: TTL index on `expiresAt`. `autoIndex` is off in production: run `npm run db:indexes` on every deploy (it creates missing indexes and drops removed ones).

**Rules**

- Enums are strings defined once in `src/lib/constants/enums.ts` and used by Mongoose and Zod. Money is whole rupees in `...Pkr` fields; dates are UTC.
- Embed small data always read with its parent; reference anything shared or unbounded. Save the actor's name beside their ID in notes, history and audit entries.
- CNIC numbers and financial details are excluded from list queries by projection, lists show only the last four CNIC digits, and neither is ever logged.
- `sanitizeFilter` is on, so an object such as `{ "$ne": "x" }` in a request cannot act as a query operator.
- References to staff are `ObjectId`; Better Auth's own `user.departmentId` is a string, so convert when comparing with an office `_id`.

**Seeding:** `npm run db:seed` is safe to repeat. It creates the five offices (draft mandates, open-questions C25), default settings (letterhead contact details, **unconfirmed**) and, if no Super Admin exists, asks for the first one's email and password (or takes `--email` and `--password`) and stores the account in the database. Existing offices and settings are never overwritten. `npm run db:seed:sample` adds clearly labelled sample programs, institutions, vacancies, research, news, FAQs and impact numbers for development and CI; it refuses to run when `NODE_ENV=production`. Cache tags for public content (`settings`, `departments`, `programs`, `institutions`, `vacancies`, `publications`, `news`, `faqs`) are in `src/lib/constants/cache-tags.ts`; every service that changes content must call `revalidateTag(tag, { expire: 0 })` for its tag after the write (see architecture.md). **Filters:** Mongoose `sanitizeFilter` turns query operators into plain values, so server-built operators (`$gte`, `$in`, `$text`) are wrapped in `mongoose.trusted()` and user input never is. It rewrites the filter object in place as soon as a query is created, so `.setOptions({ sanitizeFilter: false })` afterwards is too late; a filter shared by an `aggregate` list and its `countDocuments` marks every operator object trusted (the driver ignores the marker).

**Changing a schema safely:** add fields as optional or with defaults; run `npm run db:indexes` if an index changed; when existing documents must change, write a one-off script in `scripts/migrations/`, run it once and note it here; never remove a field in the same release that stops writing it.

## Status workflows

Every status change records who, when and why. Applications, job applications and directives are archived, never deleted.

| Record            | Flow                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Who                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Application       | Built (Phase 6). Submitted → Under review → Verified → Recommended → Approved or Rejected. Under review ↔ Incomplete (applicant uploads missing items from `/application-status`, which returns it to Under review). Rejected also from Under review, Incomplete and Verified (open-questions D25). Withdrawn before a decision. Verified needs a complete checklist. The map is `APPLICATION_TRANSITIONS` in `src/lib/constants/application-workflow.ts`                                                                       | Staff review, verify, recommend; Director and CEO Office decide                                                |
| Scholarship award | Built (Phase 6). Created in the same transaction that approves a scholarship application. Active, On hold, Ended; amount per period, start and renewal dates, progress notes                                                                                                                                                                                                                                                                                                                                                    | Admissions & Scholarships                                                                                      |
| Vacancy           | Built (Phase 6). Draft → Published → Closed, and Closed → Published (reopen). A published vacancy past its deadline (the end of that day, Pakistan time) shows as closed everywhere, with no job to run. Only a draft nobody applied to can be deleted. The map is `VACANCY_TRANSITIONS` in `src/lib/constants/vacancy-workflow.ts`                                                                                                                                                                                             | Staff create and edit drafts; only a Director publishes, closes, reopens or edits a published vacancy          |
| Job application   | Built (Phase 6). Received → Shortlisted → Interview → Selected; Rejected and On hold from every open stage; On hold returns to Shortlisted or Interview. An interview time can be set while Shortlisted, Interview or On hold. Archived applications are read-only until restored. Selection records a recommendation only; candidates are not emailed about status changes. The map is `JOB_APPLICATION_TRANSITIONS` in `src/lib/constants/job-application-workflow.ts`                                                        | HR & Teacher Management Staff and Director; the CEO Office reads                                               |
| Directive         | Built (Phase 6). Per target office: Pending acknowledgement → Acknowledged → In progress → Completed. While the part is open, the office's Director may request clarification with a reason (law, constitutional documents, Board resolution, donor restriction, operational impossibility); the CEO Office reopens it (back to the status before the request) or closes it (Closed, the office is released). Overdue: past the due day with the part not Completed or Closed. Map in `src/lib/constants/directive-workflow.ts` | Research & Policy Institute issues; each office's Director acknowledges, assigns, responds; Staff post updates |

## Emails

React Email templates with the OEDF logo and a plain-text version, sent through Nodemailer (SMTP, `SMTP_URL`). A failed send is logged (subject only, never the address) and never fails the submission. A contact message goes to the office's `notificationEmail`, else the general email in Settings; with neither it is only saved to the inbox.

| Email                                                           | To                                                                                    | Phase |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----- |
| Application received (reference number, status link)            | Applicant                                                                             | 4     |
| Documents missing (lists the items, status link)                | Applicant                                                                             | 6     |
| Application approved, application rejected (no internal reason) | Applicant                                                                             | 6     |
| Job application received                                        | Candidate                                                                             | 4     |
| New contact message                                             | The matching office's notification email                                              | 4     |
| Staff invitation (set-password link), password reset            | Staff                                                                                 | 5     |
| Directive issued                                                | Directors of the target offices (or the office's notification email when it has none) | 6     |
| Clarification requested                                         | CEO Office users (or its notification email)                                          | 6     |
